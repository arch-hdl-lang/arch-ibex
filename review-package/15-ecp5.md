# 15 — ECP5 FPGA synthesis and place-and-route (TASK2 Phase 5)

Run 2026-09-04 with `flow/ecp5_pnr.sh` (stages `synth`, `pnr`, `all`),
same source lists, parameter overrides and sv2v outputs as the sky130
flow (`14-sky130.md` §4.1–4.2). Tools (`10-toolchain.md`): Yosys
0.67+post (`synth_ecp5`), nextpnr-ecp5 8dbcee5 built from source
(2026-08-31 upstream), prjtrellis 1.4 (Homebrew). Target device
LFE5U-85F (`--85k`), speed grade 6, clock `clk_i` constrained to
**50 MHz** on both lanes with `--timing-allow-fail` so that a
constraint miss still yields a routed design and an fmax figure.

**Memory mapping is identical on both lanes** (the task's stop
condition): the four icache arrays (2 ways × 256 × 64-bit data, 2 ways ×
256 × 22-bit tag) map to 6 DP16KD blocks on each lane, the multiplier to
one MULT18X18D on each lane, and no distributed-RAM LUTs are used
(`RAM LUTs: 0` in every nextpnr log). On the SV lane the memories are
upstream's `prim_generic_ram_1p`; on the Arch lane they are the
`ram` construct of `IbexIcache.arch`, which the compiler emits as a
plain `always_ff` array and Yosys infers the same way. The register file
(32 × 32-bit FF file, `RegFile 0`) stays in flops on both lanes.

Arch lane's version of that path is about 4–5 ns longer (≈ 34.3 ns vs
≈ 29.8 ns clock period at the mean fmax); which stage of it grows was
not analysed.

## 5.3 Substitutions and caveats (read before quoting a number)

1. **Clock-gate primitive replaced by a pass-through on both lanes.**
   Upstream's `prim_generic_clock_gating` is a latch-plus-AND gate;
   `synth_ecp5` cannot map a latch and the ECP5 has no fabric clock-gate
   cell, so `flow/ecp5_prim_clock_gating.v` overrides the module with
   `assign clk_o = clk_i;` (no gating, `en_i`/`test_en_i` unused). The
   core clock is therefore free-running in the FPGA lane; the sky130
   lane keeps the real gate. Applied identically to both lanes; approved
   by the owner in the Phase 5 session.
2. **Out-of-context placement.** `ibex_top` has 787 (SV) / 2,000 (Arch)
   top-level IO bits; the largest ECP5 package has 365 IO cells
   (`TRELLIS_IO: 0/365` in the logs) and a first attempt with
   `--lpf-allow-unconstrained` alone failed with "no BELs remaining to
   implement cell type 'TRELLIS_IO'" at `hart_id_i[2]`. The runs above
   use nextpnr's `--out-of-context` mode: no IO buffers are inserted,
   ports become internal nets, and no bitstream is written. Register-to-
   register timing through the core is unaffected; there is no I/O
   timing in these numbers. The 788 / 2,001 warnings in the logs are the
   per-port "unconstrained in LPF, will be automatically placed" notices
   (787 / 2,000 ports) plus the fmax warning.
3. **The Arch lane's top exposes RVFI ports unconditionally.** Upstream
   `ibex_top` hides its 38 `rvfi_*` outputs behind `ifdef RVFI` (off in
   both lanes); the ported `IbexTop.arch` declares them always and ties
   them to constants (spec note N-1, `14-sky130.md` §4.1). Out-of-context
   these 1,213 extra constant outputs disappear at packing (no IO cells,
   no logic), so the Arch lane's numbers in §5.2 are not inflated by
   them. They do affect the sky130 P&R lane (extra top-level pins and
   tie-off cells); see `14-sky130.md` §4.4.
4. **Utilisation.** Both lanes use ≤ 20 % of the 85k LUTs, so the fmax
   figures are not congestion-limited; seed-to-seed spread is 1.2 MHz
   (SV) and 1.5 MHz (Arch).
5. **What this lane says about the port.** On ECP5 the Arch lane needs
   1.53× the LUT4s, 1.35× the flops, the same block-RAM/multiplier
   budget, and runs at 0.87× the clock. The flop delta (+896) is of the
   same size as the sky130 non-RAM flop delta (+931, `14-sky130.md`
   §4.3); a per-module attribution of those flops was not measured. The
   LUT ratio is larger than the sky130 cell-area ratio (1.09×) because
   on sky130 the RAM arrays (mapped to identical enable-flop
   populations on both lanes) dominate the area, whereas here they sit
   in block RAM and only the control/datapath logic is counted.

## 5.4 Re-run after Phase B (RVFI ports removed from the Arch top; TASK3 B5, 2026-09-05)

Same script, same tools, same seeds. The SV lane was re-run in the same invocation
and reproduced §5.1–5.2 exactly (LUT4 9,963, COMB 11,221, FF 2,534, fmax 34.36 /
33.13 / 33.19 MHz), so the flow is deterministic for an unchanged input. The Arch
lane now synthesises the RVFI = 0 `ibex_top` (`build-synth/`, 54 ports; the
previous reports are kept as `reports/arch_ecp5_rvfi_*`).

| Arch lane | LUT4 (`synth_ecp5`) | TRELLIS_COMB | FF | DP16KD / MULT | fmax seeds 1 / 2 / 3 (MHz) | mean | Report |
|---|---|---|---|---|---|---|---|
| RVFI ports present (§5.1–5.2) | 15,751 | 17,033 | 3,430 | 6 / 1 | 28.77 / 28.60 / 30.06 | 29.14 | `reports/arch_ecp5_rvfi_*` |
| RVFI = 0 (this run) | 15,853 | 17,135 | 3,430 | 6 / 1 | 28.32 / 28.52 / 27.98 | 28.27 | `reports/arch_ecp5_*` |
| delta | +102 (+0.6 %) | +102 | 0 | 0 | | −0.87 (−3 %) | |

Reading: as §5.3 predicted, the ports themselves cost nothing out-of-context (they
were dropped at packing before, 2,001 → 788 "unconstrained IO" warnings now). The
+102 LUT4 / −0.9 MHz movement is synthesis noise from a different module boundary
(ABC re-optimises the whole flattened netlist; the seed-to-seed fmax spread alone is
1.5 MHz), not an effect of the RVFI logic — `IbexCore` ties every RVFI output to a
constant (spec note N-1), so no logic disappears with the ports. The ratios in §5.5
change from 1.53× / 0.87× to 1.53× / 0.84× (LUT4 after packing 16,969 vs 11,055;
mean fmax 28.27 vs 33.56).

## 5.5 Re-run on arch 0.72.1

Same flow; both lanes re-run. SV lane identical again (LUT4 9,963 / 11,055 packed,
FF 2,534, fmax 34.36 / 33.13 / 33.19 MHz). Arch lane (previous 0.72.0 reports kept as
`reports/arch_ecp5_v0720_*`): LUT4 15,910 (was 15,853), packed 17,026 (16,969),

init values natively).
