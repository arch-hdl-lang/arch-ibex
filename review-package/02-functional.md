## 3. Fast regression, run now on both lanes

Chosen regression (< 1 min per lane): `tests/test_soc_lint.py` +
`tests/test_cpu_programs.py` — SoC lint plus the 10 end-to-end CPU
programs. This is items 2–3 of the per-swap gate in `README.md`
("Verification gate per swap"). The per-module unit suites and the
74 arch tests only apply to the Arch lane (they load `build/*.sv`);
they were not run here (see §4).

Lane selection uses the harness's own rule (`tests/conftest.py:235`):
every `build/*.sv` shadows the upstream file of the same name, so the
Arch lane is "`make build` populated" and the SV lane is "`build/`
emptied". Both lanes use the same SoC glue, the same generated
CLINT/PLIC (generated by the same `arch` binary), and the same
`ibex_top_tracing` parameters.

Command (run from the repo root, once per lane):

```
ARCH_BIN=<scratch>/arch-com-B/target/release/arch \
PATH=/opt/homebrew/anaconda3/bin:$PATH \
pytest tests/test_soc_lint.py tests/test_cpu_programs.py \
       -p no:cacheprovider -v --junitxml=review-package/reports/functional_<lane>_lane.junit.xml
```

### Arch-lane simulation failure detail

All ten programs stop at the same point, within the first 140 ns of
simulation (14 clock cycles), before any program instruction is
retired:

```
[140000] %Fatal: fb_age_arb.sv:75: Assertion failed in
  ibex_mini_soc.u_ibex.u_ibex_top.u_ibex_core.if_stage_i.icache.bus_arb.g_auto_hs_request[2]._auto_hs_request__lane_valid_stable:
  HANDSHAKE VIOLATION (valid must stay asserted until ready): FbAgeArb._auto_hs_request__lane_valid_stable
%Error: build/fb_age_arb.sv:75: Verilog $stop
```

The assertion is not in the design source. It is emitted by the ARCH
compiler for every `handshake_channel` port of an `arbiter`
("Auto-generated handshake protocol assertions (Tier 2)",
`build/fb_age_arb.sv:71-77`). It asserts the valid/ready rule that a
requester holding `valid` high must keep it high until `ready`. The
icache's bus-master use of `FbAgeArb` (requester lane 2) drops `valid`
before `ready` on the first fetch after reset.

Why this did not show in the recorded green gate:

| Fact | Evidence |
|---|---|
| arch-com started emitting this assertion for arbiter handshake ports on 2026-05-13 (`74e43764`) | `git -C ~/github/arch-com log -S'Auto-generated handshake protocol assertions'` |
| Verilator 5.048 evaluates concurrent assertions by default (it offers `--no-assert`; older releases required `--assert` to enable them) | `verilator --help` |
| The Verilator on this machine was installed 2026-05-26; the gate of 2026-05-13 ran on an earlier, unrecorded Verilator | `ls -ld /opt/homebrew/Cellar/verilator/5.048` |
| Both compiler candidates (2026-05-14 and 2026-05-23) emit the assertion and both fail the same way | `reports/functional_arch_lane.log` (B); earlier run with A, identical |

So the Arch lane contains a valid/ready protocol violation in the
icache → arbiter interface that the compiler's own generated checker
now catches.

### Arch lane with the generated checker disabled (secondary run, approved by repo owner)

To separate "protocol checker fires" from "wrong architectural
behaviour", the same harness was re-run with Verilator's `--no-assert`.
The harness does not expose that flag, so a scratch wrapper script
outside the repo (`<scratch>/noassert-bin/verilator`, a 3-line perl
script that forwards to `/opt/homebrew/bin/verilator` and appends
`--no-assert`) was placed first on `PATH`. No repo file was changed;
`git status` is unchanged. Everything else (compiler B, `build/`
contents, `ARCH_BIN`, program binaries) is identical to the run above.

| Lane | Suite | Result | Wall time | Log |
|---|---|---|---|---|
| Arch, `--no-assert` | 10 CPU programs (`tests/test_cpu_programs.py`) | **10 / 10 PASS** | 7.3 s | `reports/functional_arch_lane_noassert.log`, `.junit.xml` |
| Arch, `--no-assert` | RISC-V arch tests rv32i_m I/M/C vs upstream-generated signatures (`tests/test_arch_tests.py`) | **74 / 74 PASS** (39 I, 8 M, 27 C); 74 reference-generation variants skipped by design | 19.7 s | `reports/archtests_arch_lane_noassert.log`, `.junit.xml` |

The arch-test pass means that, with the checker disabled, the Arch
core computes bit-identical architectural signatures to upstream Ibex
on all 74 compliance programs (references were generated from
upstream Ibex in the same SoC; `tests/test_arch_tests.py:10-27`).

Reading of the two Arch-lane rows together: the design's observable
behaviour matches upstream on every program tried; the failure with
assertions enabled is a real interface-contract violation (the icache
retracts a bus request to its own arbiter before it is granted) that
is benign for this arbiter implementation but is flagged by the
compiler's generated protocol checker. It was not visible to the
project's own gate because the gate's Verilator at the time did not
evaluate assertions by default.
