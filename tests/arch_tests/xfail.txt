# C/cebreak-01 -- the only test with a trap handler (c.ebreak). It hangs on
# BOTH the DUT and upstream Ibex in this SoC, so it has no reference.
#
#   Repro: build it (make -C tests/arch_tests BUILD=/tmp/at
#   /tmp/at/C/cebreak-01.vmem) and run it on either core; the trace
#   (trace_core_00000000.log) shows
#     pc 0x1000b4  csrrw x0, mtvec, x7     x7 = 0x00100241
#     pc 0x1000b8  csrrs x30, mtvec, x0    x30 = 0x00100241  (reads back as written)
#     pc 0x1001a4  c.ebreak                -> next pc 0x00100200, in the middle
#                                             of the init code; never halts
#
#   Root cause (RTL, soc/): the hybrid CSR file
#   (soc/ibex_cs_registers_hybrid.sv, generated from rdl2arch-riscv
#   tests/rdl/mtrap_ibex.rdl) keeps mtvec base[31:2] and mode as written,
#   but the core vectors to {mtvec[31:8], 8'h00}. Ibex's own mtvec is
#   {wdata[31:8], 6'b0, 2'b01}, so software sees a trap base the hardware
#   does not use. The framework checks that its write read back, trusts the
#   vector at 0x00100240, and the trap goes to 0x00100200.
#
#   Fixing only that is not enough: with an Ibex-exact mtvec (checked by
#   masking the write in a scratch copy) the framework sees mtvec is not
#   freely writable and copies its trap trampoline to the mtvec target.
#   Out of reset that is 0x0010_0000, so the copy overwrites the init code
#   at 0x0010_0080 that is doing it. Moving the target clear of the code
#   (an RVMODEL_BOOT change) still fails: in this framework revision
#   (a3b7f0c2) the copied range, tramp_sz, ends 16 bytes before the common
#   handler's exception branch target, so the trap lands on zeros.
